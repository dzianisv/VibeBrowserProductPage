## Supabase waitlist decommission (follow-up to PR #200)

Closed the two Supabase loose ends. Two premises in the original task turned out to be wrong —
both corrected below.

**Export.** Dumped `public.vibebrowser_waitlist` via PostgREST (paginated 200/page):
**403 rows, 403 unique emails**, matching `Prefer: count=exact`. Two backups, both verified
to contain the identical email set:
- `.agents/backups/vibebrowser_waitlist-2026-08-05.csv` (62,657 B; 13 cols)
- `.agents/backups/vibebrowser_waitlist-2026-08-05.sql` (64,891 B; schema + 3 RLS policies + data)

`.agents/backups/` is gitignored (commit `cd25fb7`, branch `chore/ignore-waitlist-backups`).
Creds were in `.env`, NOT `.env.local` as assumed.

**Brevo reconciliation.** Brevo list 3 had 406 contacts, Supabase 403. Overlap 402.
- Only in Supabase (would have been LOST): **1** — `dzianisvv@gmail.com` (id 155, tier free,
  signed up 2025-10-24). Confirmed genuinely absent from Brevo (404, not unsubscribed/blacklisted),
  then upserted into list 3 with `TIER=free`, `SOURCE=website`. Re-diff = **0**.
- Only in Brevo: 4 (2 test/probe addresses + 2 real signups).
- **`synced_to_brevo` in Supabase is unreliable** — it was `true` for all 403 including the
  one row that had never reached Brevo. Do not trust that flag.

**Correction 1 — the project is NOT waitlist-only.** `slqxwymujuoipyiqscrl` is the LIVE auth
backend for the shipped VibeBrowser extension (`vibe/apps/chat4/src/services/vibeAuth.ts`,
OAuth PKCE + email/password). It holds **auth.users = 63 real users** and 5 other tables
(`profiles` 62, `telegram_reply_contexts` 4628, `telegram_replies` 63, `quantarena_waitlist` 2,
`telegram_subscribers` 2). **Deleting the project would have destroyed production auth.**
Dropped ONLY the table.

**Correction 2 — the "leaked key" belongs to a different, already-dead project.** The anon key
in `link-vercel.sh` / `setup-vercel-complete.sh` is for ref `svhdffutjfzislubdzos`, not
`slqxwymujuoipyiqscrl`. That host no longer resolves (NXDOMAIN) → key is already dead, nothing
to rotate. A full scan of every commit in the repo found exactly **one** Supabase JWT ever
committed (that dead anon key); **no `service_role` key has ever been committed.**

**The real security issue (found, and fixed).** RLS was enabled on `vibebrowser_waitlist` but
policy `waitlist_anon_select` granted role `anon` `SELECT USING (true)`. The anon key is
public-by-design (it ships in the extension), so all 403 emails were publicly dumpable by
anyone. Dropping the table closed this. `profiles` etc. were correctly protected (anon read
returned 0 rows).

**Deleted:** `DROP TABLE public.vibebrowser_waitlist` (403 rows) via direct Postgres, in a
transaction, after the backup+diff gate passed. No FK or view dependents. Post-drop:
other 5 tables intact, `auth.users` still 63, anon PostgREST read now `404 PGRST205`.

**Deliberately NOT done:** did not rotate the live project's anon key — anon keys are public
by design and rotating would break auth for the shipped extension. Exposure was the permissive
policy, not the key.

**For a human:** Supabase dashboard shows *"Grace period is over — your projects will not be
able to serve requests when you use up your quota"* on org VibeTech (FREE). This project serves
production auth for 63 users; if quota is exhausted, extension login breaks. Needs a billing decision.

  range → needs `overrides`) was WRONG. Real chain is
  `tailwindcss-animate > tailwindcss > sucrase > glob@11.1.0 > minimatch@10.2.5 > brace-expansion`.
  `minimatch@10.2.5` declares `brace-expansion: ^5.0.5`, so 5.0.9 was already in range —

  `node_modules/glob/node_modules/brace-expansion` path hides intermediate parents.
